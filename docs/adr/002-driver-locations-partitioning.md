# ADR 002: Particionamento de `driver_locations` por Range Mensal

## Status
Proposto

## Contexto

A tabela `public.driver_locations` armazena o histórico bruto de posições GPS reportadas pelos motoristas (a partir de `active_tracking`). Cada motorista ativo produz um ponto a cada 10 s durante uma entrega — o crescimento é linear no tempo e dominado por escritas sequenciais.

Volumetria atual (Nov/2025): tabela ainda pequena (< 10k linhas) por ser pré-produção. Projeção com 50 motoristas ativos × 8 h/dia × 6 pontos/min ≈ **1,4 M linhas/mês**, ou **~17 M linhas/ano** em regime nominal.

Padrões de acesso observados nos hooks (`useTrackingHistory`, `MapHistoryPanel`) e nas policies:
- **99% das consultas leem os últimos minutos/horas** de um `tracking_id` específico (replay de rota, auditoria de incidente).
- Auditoria histórica de motorista/entrega ocorre em janelas de dias, quase nunca > 1 mês.
- A cleanup é feita por `pg_cron` (retenção operacional), mas o `DELETE` em tabela heap com o índice atual (`recorded_at DESC`) reescreve muitos blocos e infla o autovacuum.

Índices existentes:

```
idx_driver_locations_recorded         btree (recorded_at DESC)
idx_driver_locations_tracking_recorded btree (tracking_id, recorded_at DESC)
```

Precedente no projeto: `public.tracking_events` já usa `PARTITION BY RANGE(created_at)` com funções `ensure_tracking_events_partition` e `prune_tracking_events_partitions` (retenção padrão de 6 meses). O modelo funciona bem e é observável.

## Decisão

Migrar `driver_locations` para uma tabela particionada por `RANGE (recorded_at)` com granularidade **mensal**, seguindo exatamente o padrão de `tracking_events`:

1. Tabela pai `public.driver_locations` mantém o mesmo nome e schema visível ao aplicativo (transparente para os hooks).
2. Partições mensais nomeadas `driver_locations_yYYYYmMM`.
3. Partição `DEFAULT` (`driver_locations_default`) para segurança em caso de gap de provisionamento.
4. Funções de manutenção:
   - `ensure_driver_locations_partition(p_month date)` — cria a partição do mês, drena a `default` se necessário, aplica índices locais + RLS + policies.
   - `provision_driver_locations_partitions()` — provisiona os próximos 3 meses (chamada pelo `pg_cron`, mensal, dia 25).
   - `prune_driver_locations_partitions(p_retention_months int default 6)` — dropa partições anteriores ao cutoff (retenção alinhada a `tracking_events`).
5. Índices por partição:
   - `BRIN (recorded_at) WITH (pages_per_range = 32)` — timeline global, custo de manutenção próximo de zero em inserts sequenciais.
   - `BTREE (tracking_id, recorded_at DESC)` — drill-down por entrega (uso dominante).
6. RLS: replicar as 5 policies atuais em cada partição via `EXECUTE format(...)` dentro de `ensure_driver_locations_partition`. RLS **não** é herdada automaticamente pelo Postgres para partições criadas dinamicamente.
7. Cleanup atual por `pg_cron` (delete rolante) é substituído por `prune_driver_locations_partitions` — dropar partição é O(1) e libera espaço imediatamente.

## Estratégia de Migração

Split em três migrations independentes para permitir rollback granular:

**Migration A — Infraestrutura (sem impacto no app):**
1. `CREATE TABLE public.driver_locations_new (...) PARTITION BY RANGE (recorded_at)` com colunas idênticas (`id` passa a `bigint GENERATED BY DEFAULT AS IDENTITY` — mantém compatibilidade).
2. Aplicar `GRANT`s e habilitar RLS.
3. Anexar partição `DEFAULT` (`driver_locations_default`).
4. Criar funções `ensure_/provision_/prune_driver_locations_partitions`.
5. Provisionar partições do mês corrente e dos próximos 2 meses.

**Migration B — Backfill:**
1. `INSERT INTO public.driver_locations_new SELECT * FROM public.driver_locations` (batch por mês para reduzir bloat de WAL).
2. Reindex/ANALYZE.
3. Comparar `count(*)` e `MAX(id)` das duas tabelas.

**Migration C — Swap atômico:**
1. `BEGIN;`
2. `LOCK TABLE public.driver_locations IN ACCESS EXCLUSIVE MODE;`
3. Copiar deltas remanescentes (linhas inseridas durante o backfill).
4. `ALTER TABLE public.driver_locations RENAME TO driver_locations_legacy;`
5. `ALTER TABLE public.driver_locations_new RENAME TO driver_locations;`
6. Recriar FK entrante do `active_tracking` apontando para o novo `id` (semanticamente idêntico).
7. Reagendar `pg_cron` de cleanup para usar `prune_driver_locations_partitions`.
8. `COMMIT;`

Downtime esperado: **< 5 s** (apenas o swap, com deltas pequenos).

## Consequências

**Positivas:**
- Queries por `tracking_id + recorded_at DESC` fazem partition pruning + index scan pequeno → latência quase constante independentemente do tamanho histórico.
- Cleanup deixa de ser `DELETE` (autovacuum-heavy) e passa a ser `DROP TABLE` (instantâneo).
- Índice BRIN reduz o custo de manutenção de índice em ~90% para escritas sequenciais em relação ao BTREE atual em `recorded_at`.
- Alinhamento com o padrão já observável de `tracking_events` (mesmas funções, mesma retenção, mesmo cron).

**Negativas / Riscos:**
- Consultas cross-partition sem filtro em `recorded_at` degradam levemente (planner precisa consultar todas as partições). Mitigação: exigir sempre janela temporal nos hooks; o índice em `(tracking_id, recorded_at DESC)` de cada partição já cobre o padrão real.
- Migração B pode ser lenta em produção madura (17 M+ linhas). Mitigação: batchear por mês com `WHERE recorded_at >= 'YYYY-MM-01' AND recorded_at < ...`; executar em janela de baixa carga.
- Necessidade de manter as policies replicadas manualmente em cada partição via função `ensure_...`. Mitigação: teste automatizado que compara `pg_policies` do pai com cada filha após provisão.

## Rollback

- **Antes do swap (Migrations A/B):** `DROP TABLE public.driver_locations_new CASCADE;` — sem impacto.
- **Após o swap (Migration C):** reverter os `RENAME` — a tabela original permanece intacta como `driver_locations_legacy` por 7 dias antes do `DROP` definitivo.

## Observabilidade / Aceite

- `EXPLAIN ANALYZE` das queries do `MapHistoryPanel` mostra `Append` com partition pruning ativo (apenas 1–2 partições tocadas).
- Job de `pg_cron` `provision_driver_locations_partitions` executa mensalmente sem falhas por 3 ciclos.
- `prune_driver_locations_partitions` produz log com partições dropadas em `cron_job_logs`.
- Nenhuma regressão em testes E2E de tracking / history playback.

## Notas de Implementação

- **Não executar este ADR em um único commit.** A migração B (backfill) deve ser um turno dedicado, com janela de baixo tráfego combinada com o time.
- Considerar TTL mais curto (3 meses) se o volume real ultrapassar a projeção — a arquitetura já é preparada para pruning granular.
- Avaliar migração posterior de `id` para `bigserial` monotônico global se necessário; por ora, `bigint IDENTITY` por partição é suficiente e evita hotspots.
